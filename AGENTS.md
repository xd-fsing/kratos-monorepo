# Repository Guidelines

This is a Kratos microservices monorepo. This file owns the layering and
service-boundary contract agents must follow when changing the repo.

## Project structure

```
api/<domain>/<version>/   Proto sources and generated stubs. Public contracts
                          shared by every service.
apps/<service>/           One deployable service per directory.
  cmd/<app>/              Entrypoint, Wire injector, main.go.
  configs/                Runtime config (config.yaml). No secrets.
  internal/conf/          Config proto; generated by `make config`.
  internal/server/        HTTP/gRPC registration (thin; construction lives in
                          pkg/server).
  internal/service/       Transport adapters: validation, business rules,
                          orchestration over the data stores.
  internal/data/          Store types, ent schemas and implementations,
                          gRPC clients of other services, typed errors.
pkg/                      Service-agnostic shared libraries.
openapi/                  Merged OpenAPI document (generated).
Makefile, buf.*.yaml      Build and codegen entrypoints.
```

## Layering & dependency rules

Two layers. `service` owns validation, business rules, and orchestration;
`data` owns the store types, storage, and external clients. The proto
types from `api/` are the model that flows between them.

```
   client ──► DTO ──► service ──► DTO ──► data ──► PO ──► storage

   DTO  Data Transfer Object — proto request / response; also the in-process
        model, so there is no separate domain struct to convert.
   PO   Persistent Object    — storage shape (ent types), owned by `data`.
```

| Layer   | Owns                                  | Never speaks                        |
|---------|---------------------------------------|-------------------------------------|
| service | validation, business rules, orchestration | PO, storage client, *Data          |
| data    | store types, PO, typed errors, storage clients | — (api DTOs are its model)   |

- `service` imports `api/...` (DTO) and the `data` package for its store
  types (`*data.TodoStore`, `*data.UserStore`). It never touches
  `*data.Data`, PO types, or storage drivers.
- `data` declares the store types next to their storage code. It imports
  `api/...` freely: DTOs are the model it persists and returns.
- `cmd` is the only place that wires all layers via Wire.
- `pkg/` holds only service-agnostic code and must not import `apps/*` or
  `api/*`. Shared transport construction and middleware live in
  `pkg/server`; each app's `internal/server` only registers its services.

A change crossing these arrows the wrong way is a layering bug; fix the
design rather than add the import.

### Service boundaries (monorepo)

- One app = one database. Never reach into another service's storage: no
  shared tables, no cross-service ent clients.
- Cross-service calls go through `api/` contracts only. The client wrapper
  store lives in the calling service's `data` layer (reference:
  `apps/todo/internal/data/user.go`); the orchestration that uses it lives
  in `service` (`apps/todo/internal/service/todo.go`, CreateTodo). Never
  import another app's `apps/<other>/internal/...`.
- Config protos are per service, and the proto `package` must be unique per
  service (e.g. `todo.conf`, `user.conf`): two services registering the
  same message name panic at init when linked into one binary.

### Layer responsibilities

**service (DTO in, DTO out)**

- One file per resource. Embed `Unimplemented<Resource>ServiceServer`.
- Validate request inputs at the boundary (required fields, id formats,
  `filter` / `order_by` / `page_token` parsing, `fieldmask.Update` for
  partial updates).
- Own the business rules and multi-step orchestration, e.g. checking an
  owner exists through another service before writing (CreateTodo).
- Hand parsed AIP query parts (`filtering.Filter`, `ordering.OrderBy`,
  offset, limit) to the Store's list method and build the reply (usually
  the resource itself or a `<Resources>Set` wrapper).
- Return `data` typed errors. No storage access, no PO, no `*data.Data`.

**data (Store interface + implementation)**

- _Store shape_: declare `type <Resource>Store struct` with its methods in
  one file; the constructor returns the concrete type:
  `func New<Resource>Store(d *Data) *<Resource>Store`. Store methods speak
  proto types only: DTOs as the model, ids as proto `string`s, page size
  as `int32`. The parsed AIP query structures (`filtering.Filter`,
  `ordering.OrderBy`) are the one non-proto type that crosses the boundary.
  Implementations parse ids defensively (`uuid.Parse` → the resource's
  invalid-argument error).
- _Errors_: own the typed errors for the resource (`Err<Resource>NotFound`,
  `Err<Resource>InvalidArgument`, ...) built with kratos `errors.*` plus
  the api error reason enum. `service` reuses them for boundary
  validation.
- _PO and conversion_: ent types stay inside `data`. Convert inline at the
  read site (PO → DTO at the return, DTO → builder on writes); no shared
  conversion helpers. Driver-specific builder types never leave `data`.
- _Shared clients_: `*Data` (declared in `internal/data/data.go`) holds
  long-lived storage clients. Stores receive `*Data` and never construct
  their own clients.
- _External service clients_: wrap dependency gRPC clients in a store type
  and map RPC errors to typed errors (`apps/todo/internal/data/user.go`).
  The target address comes from the service's conf `client` section.
- _Querying_: translate the `filtering.Filter` and `ordering.OrderBy`
  received from `service` into the storage driver's query language.

**server**

- Register the app's services on HTTP/gRPC servers built by `pkg/server`.
  No translation, no business logic, no middleware changes.

### Add-a-service checklist

1. **Skeleton**: `make service app=<name>` scaffolds a compiling, runnable
   empty service (cmd, configs, conf proto, ent plumbing with a placeholder
   `Example` schema, thin server/service/data layers) and generates its
   conf stub, ent client, and wire injector. Replace the placeholder schema
   with your own.
2. **DTO**: define the service's protos in `api/<domain>/<version>/`, then
   `make api app=<name>`.
3. **Storage**: write the ent schema, then regenerate the ent client:
   `go generate ./apps/<service>/internal/data/ent`.
4. **Store**: declare the `<Resource>Store` type in `data` with its
   methods on top of `*Data` (or a gRPC client for dependencies), and
   register the constructors in `data.ProviderSet`.
5. **Service**: validation and business rules over the stores; register
   the constructor in `service.ProviderSet`; register HTTP/gRPC services in
   `internal/server`.
6. **Wiring**: add `data.ProviderSet` + `*conf.Data` and
   `service.ProviderSet` to the build in `apps/<service>/cmd/wire.go`
   (the scaffold starts with `server.ProviderSet` only — wire rejects
   empty or unused sets), then regenerate `wire_gen.go` by running wire in
   that cmd directory once.
7. **Regenerate**: `make all` to refresh Wire and `go.mod`. Build targets
   pick the new service up automatically (`SERVICES` is derived from
   `apps/`).

## Generation & generated files

Regenerate via `make api`, `make config`, or `make all`; never hand-edit
`*.pb.go`, `*_grpc.pb.go`, `*_http.pb.go`, or `wire_gen.go`. `wire_gen.go`
is created by running wire once in a new service's `cmd` directory. buf
does not remove stale outputs — delete obsolete generated files by hand.
Keep ent fields free of GoType bindings to other packages: the generator
emits unused imports for them in some files.

## Naming & error reasons

- Resource: `<Resource>` (e.g., `Todo`); collection RPC:
  `List<Resources>`.
- Types: store `<Resource>Store`, service `<Resource>Service`.
  PO types are the ent generated types inside `internal/data/`; convert
  inline at the read site.
- Error reasons: declared in `api/<domain>/<version>/error_reason.proto`,
  surfaced as `Err<Resource><Cause>` in `data`.

## Commits & security

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `chore(deps):`,
  `docs:`, `test:`. Regenerated files belong in the same commit as
  their source.
- Never commit real credentials in `configs/config.yaml`.
